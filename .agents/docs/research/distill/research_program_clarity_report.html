Traces to training data: the scenario system, explained

This branch turns ~1,000 recorded agent conversations into machine-gradable training scenarios, trains an agent on its own judged successes inside a learned simulator, and measures everything against a baseline built to be un-foolable.

Impact: a 9B customer-service agent improves from 41.4% → 47–49% task success using no teacher model and no human labels — only its own filtered rollouts. All four independently trained adapters beat base (+3.6 to +10.4, mean +6.5; 222 rollouts per model = 74 specs × 3 passes) — consistent direction, though below the apparatus's own significance bar (§6). The same apparatus established that the pipeline's scenario selection step adds nothing over random choice, redirecting the roadmap toward scenario generation.

Colors, used consistently below: DATA — making specs and training rollouts MEASUREMENT — judging models fairly
Vocabulary (used throughout): a spec is a scenario's task — a general parameterization of the simulator; a rollout is the artifact an agent produces against it (think/tool/response steps); criteria are the checklist a judge grades a rollout against.

1 · The problem this solves

In one line: recorded traces can't train well (one fixed path per task) or evaluate at all (no success criterion) — so the system converts each trace into a spec + criteria, and everything downstream follows from that conversion.

The raw material is OpenTelemetry traces of tool-using customer-service agents, mined into scenarios (spec + seed state + criteria) and used twice: on the data side to manufacture training rollouts, and on the measurement side to score models reproducibly.

2 · The big picture

In one line: five stages — mine, synthesize+validate, self-collect, fine-tune, evaluate — with the simulator and the judge appearing at every stage after the first.

3 · The one trick: criteria are the universal contract

In one line: one data-format decision — every spec ships with machine-gradable criteria — lets a single judge power validation, training-data filtering, and evaluation, so improvements to any of them compound.

Scenario = spec + seed state + criteria
criteria are externally checkable outcome statements
judge.score(spec, criteria, rollout_steps) → pass_rate, success
at build timeValidity gate
Judge checks the criteria against the source trace; disagreement kills the scenario.
at collection timeTraining filter
Only rollouts passing every criterion become training data — no human in the loop.
at eval timeThe metric
Success = all criteria pass; pass-rate = fraction passed. Same judge, every arm.

4 · Implementation details

In one line: how mining actually works, how the simulator generalizes beyond recorded traces, and the exact collection, training, and measurement parameters as shipped.

4.1 How scenarios are mined

Four steps from raw traces to a scenario pool:

  • Facet extraction — a cheap LLM reads a digest of each trace and emits a ≤30-word task summary; code (not the LLM) computes the tool-call signature, domain, and outcome. The embedded text carries the capability, not the phrasing: 
    def embed_text(self) -> str:
    # "[retail] Exchange a delivered laptop | tools: find_user>get_order>exchange_items"
    parts = [f"[{self.domain}]"] if self.domain else []
    parts.append(self.task_summary)
    text = " ".join(parts)
    return f"{text} | tools: {self.tool_signature}" if self.tool_signature else text
    This single change — embedding domain + tools alongside the summary — moved mined selection from clearly behind random (22.2% vs the 30.2% ± 5.5 random mean on the earlier eval pool, with retail collapsing to 0%) to parity (48.6% vs 47.4% ± 3.8 on the frozen pool).
  • Clustering — deterministic k-means (kmeans++ init) over L2-normalized facet embeddings, so distance ranks like cosine similarity.
  • Selection — near-duplicate facets inside a cluster are dropped first (SemDeDup: embeddings within cosine 0.95 of a kept one are discarded); then 70% of the budget goes to clusters proportional to their mass and 30% round-robin for tail coverage; the first pick per cluster is its medoid, extra picks go farthest-first, and every failure category keeps at least one exemplar.
  • Synthesis — for each selected trace, gpt-5.4 writes the spec (customer, goal, constraints), the seed state (entity facts the simulator honors), and 4–6 criteria; the inline validity gate (§3) judges the criteria against the source trace before the scenario may exist.

4.2 The simulator, and why specs generalize

The simulator (the "world model") is not a replay of traces. It is an LLM (gpt-5.4) behind a fixed environment prompt, with a retriever pulling the 5 most similar recorded steps from the corpus as grounding for each tool call. That construction defines a continuous conditional distribution over tool responses given the spec, seed state, and action history: even tool calls never observed together in any single trace get a plausible response interpolated from retrieved neighbors. A spec is therefore a true parameterization of the simulator — any well-formed spec instantiates a runnable environment. The system relies on this twice: six attempts at one spec explore genuinely different rollouts, and synthesized specs with recombined entities remain simulatable.

4.3 The collection loop

# collect_bc.py — the numbers that matter
samples per spec       6      (temperature 1.0)
keep per spec          ≤ 2    passing rollouts, ranked by (pass_rate desc, fewer turns)
student max_tokens     10240  # reasoning eats budget; lower values yield 0-step rollouts
judge max_tokens       8192   # reasoning judges truncate verdicts mid-JSON below this
max rollout steps      10
final message          appended as a judged step  # "inform the customer" criteria live there

Kept rollouts preserve the student's private reasoning; the student must be served with vLLM's --reasoning-parser qwen3, which the collection code depends on for clean targets.

4.4 The training recipe

# train_sft_box.py — identical for every arm
LoRA        r=32, alpha=64, dropout=0.05, all attention+MLP projections
optimizer   lr=1e-4 cosine, warmup 3%, 3 epochs, effective batch 8
loss        completion-only; prompt = chat history with PRIOR think-blocks stripped
            (matches inference distribution); target keeps its think-block
precision   bf16, gradient checkpointing, max_length 8192, save_strategy="no"
scale       ~60–75 rollouts → 200–320 per-turn samples → ~25 min on one H100

4.5 The measurement apparatus

  • Frozen eval pool: 74 validated scenarios from the hash-disjoint eval split (59 telecom / 9 airline / 6 retail), committed at 4adc4b5, immutable.
  • Multi-seed baseline: the random comparator is three independently drawn, fully trained arms — 45.0 / 51.8 / 45.5 → 47.4% ± 3.8 success. Single draws are never baselines: on a smaller earlier pool, single-seed rankings inverted entirely when the pool grew.
  • Pre-registered decision rule: "beats random" requires a paired per-spec delta > 2× the seed spread (7.6 pts) with sign-test p<0.05. All numbers are means of 3 passes; budgets are matched across arms.

6 · What training through the system buys

In one line: self-trained adapters beat the base model by 4–10 points depending on the draw (mean +6.5), verified at 222 rollouts per arm on the frozen pool.

Two honesty notes. First, the 7.6-point rule (§4.5) governs method-vs-method claims; the base-model lift rests on consistency — all four adapters beat base — but its paired per-spec test is not significant (36W/25L/13T, p=0.20): strong evidence, not proof beyond noise. Second, mined and random selection perform equivalently (paired 33W/27L/14T — inside noise; §10).

7 · How the design protects its own numbers

In one line: the components most able to silently corrupt results — the judge, the serving stack, and the simulator — each carry a structural guard.

  • The judge sees everything it grades: the final user-facing message is a judged step, and the verdict budget is 8K tokens (below that, truncated verdicts read as silent failures). Enforced with a regression test.
  • Reasoning separation is load-bearing: without the serving-side reasoning parser, think-text leaks into training targets undetectably; a smoke generation checks it before any collection.
  • Nothing can leak or drift: the simulator is frozen during rollouts, train/eval traces are hash-disjoint by construction, and baselines can't be cherry-picked — frozen pool in git, 3-seed mean, decision rule that predates every arm it judges.

10 · Limitations & future work

In one line: the open problems are the selection question, the simulator boundary, and the single judge — and the next arm (skill-based generation) is chartered with its main design obstacle identified.

Limitations

  • Selection doesn't yet earn its complexity: the pipeline's proven value is scenario construction, not training-data selection.
  • Everything lives inside the simulator; claims here are about simulated performance. Method-level effects under ~7.6 points are undetectable by design — sensitivity traded for trustworthiness.
  • The judge is a single point of epistemic failure: one model family grades validation, filtering, and eval; a judge blind spot would be invisible to every metric.
  • Collection wastes budget at the extremes: never-passed specs contribute nothing (13–28 of 60 slots per draw); always-passed ones contribute redundancy.

Future work (chartered, in priority order)

  • Skill-extraction generation (next arm): exploit the simulator's continuous distribution (§4.2) — synthesize novel specs from a skill inventory rather than replaying traces; the one approach with a teacher-controlled, budget-matched win over random selection in the literature (Instruct-SkillMix). Blocking problem: generated specs have no source trace for the validity gate; planned replacement: skill-spec agreement + solvability probe + embedding dedup against the frozen eval pool.
  • Difficulty-aware budget reallocation: shift rollouts toward the ~12.5–87.5% pass-rate band (DART-Math / HS-STaR); expected +1–2 pts, so it rides along rather than leads.
  • Failure-contrast training: passing/failing rollout pairs on the same spec are preference-learning signal at zero extra collection cost.

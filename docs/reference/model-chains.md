# Ordered model chains

A direct Chat Completions, Responses, or Messages alias can reference another model's provider chain when an explicitly enforcing host authorizes execution. Generic local SQLite chain execution remains unsupported; draft authoring and plain-alias serving remain available. Image generation, embeddings, decisions, and project selection do not gain cross-model traversal. Image, embedding, and decision requests whose selected root carries chain policy are refused before acceptance, including explicitly unavailable chains; independent plain roots in the same catalog keep exact-model serving. Provider pools still certify only one exact model; a model reference is not equivalence certification.

## Configuration

`ModelCatalog.gateway_model_chains` holds `GatewayModelChain` records keyed by canonical model ID. Each record names its exact-model pool, revision, optional frozen `ModelStagePolicy`, and ordered rungs. A rung is either `GatewayDeploymentRung(deployment_id=...)` or `GatewayModelReferenceRung(model_id=...)`.

A chain permits at most one reference and requires a direct first rung. The child can reference another model. Reciprocal links are legal. Execution marks canonical models visited, skips a reference to an entered model, and resumes the parent's remaining providers when the child is exhausted:

```text
A: a1, reference B, a2
B: b1, reference A, b2

Order after eligible failures: a1, b1, skip repeated A, b2, a2
```

Expansion allows at most sixteen distinct canonical models and 256 examined rungs. A resumed parent suffix forms another execution segment without counting as another canonical model. The request keeps one deadline and an eight-attempt total cap. Skipped references are not provider attempts. No later settlement rewinds an in-flight request.

## Admission and policy

`ExecutionSnapshot.model_stages` freezes model, selected pool, providers, policy, revision, ancestry, and rung positions. `stage_for_depth()` identifies the destination for a physical attempt. Narrowing removes unsupported providers while preserving surviving stage boundaries. Affinity and cache-marker ordering operate inside a segment, never across a reference.

Each stage owns its failover mode, cache threshold, and throttle-redial schedule. A child cannot inherit the root's schedule accidentally. Sticky and reasoning-pinned providers receive their own stage's full redial allowance; the final admitted provider receives its own full allowance too. Every retry still consumes the shared request attempt cap. Exhausting scheduled redials advances rather than reapplying the no-schedule cache-threshold rule.

A live reasoning issuer retains first position after authorization and capability narrowing. Cache or affinity preferences cannot demote it before a real eligible failure. A filtered issuer is not restored. A default lane bound or authored `saturation="refuse"` policy refuses a saturated reasoning issuer rather than bypassing capacity or stripping reasoning to switch providers. Recovery trials require the same default or authored lane headroom. Following an eligible failure, authorized compatible successors can run with provider-bound reasoning removed as required by the existing continuation contract. Semantic commitment, including a tool-call start, ends fallback eligibility even before client receipt is confirmed.

Default lane bounds and authored `saturation="refuse"` bounds are hard limits on ordinary routes as well as model chains. Reasoning pins and forced retries cannot exceed them. Explicitly permitted soft overflow remains distinct from these hard bounds; authored chains do not grant an exception.

## Accounting and recovery

Each provider call retains the requested alias while its attempt records the actual stage model, pool, prices, and usage. `x-gateway-canonical-model` identifies the model that produced the committed response. Root and destination budget scopes both apply, with equal scopes deduplicated. Hosted stores must implement the same stage checks at their atomic reservation boundary; authoring a reference never grants access or money. A platform-funded child requires valid host-funded root admission. If root routes were skipped, customer-managed, or refused before that admission, the child remains refused; the engine does not invent a root attempt or undo spend to bypass funding.

Capture keeps the requested root model in `CaptureRequest.model_id`. The existing terminal `deployment_id`, actual-model response header and attempt ledger identify a child winner; no separate canonical-winner field is added. Default capture uses full schema-1 records. A host-funded winning lane requires durable prompt acknowledgement before public output; a customer-managed winning lane does not create that hosted prompt checkpoint. Explicit `asynchronous_delivery=True` waits for queue admission instead, while the accepted capture owner remains charged until storage acknowledgement. Opt-in schema 2 contains completion references without repeated context, not a different winner identity contract. Cancellation or a rejected checkpoint closes upstream work without making terminal capture retention wait on storage; it does not acknowledge a successful checkpoint or release accepted retention early. The sink remains responsible for live consent, idempotent updates and deletion of previously durable content.

`RecoveryHost` supplies immutable, already-loaded transport observations and preallocated leases. `CredentialEnvironment.resolve_credential` returns authentication and an opaque worker-local binding receipt together; an authoritative missing result never falls through to another credential source. Static wire profiles freeze that receipt before recovery selection and retain it through direct and swept settlement. Profiles without a receipt, including unbound refreshable signers, serve normally but provide no elective recovery or cache warmth. Shared `OperationalScope` contains only exact resolved endpoint/model/known region topology; the local credential receipt and tenant identity are excluded. Shared account-specific recovery is unavailable without a stable generation returned atomically with the credential. Requests or operator wire profiles carrying `inference_geo` supply no recovery binding until their execution geography can be proved against the resolved wire; their normal provider payload and serving behavior remain unchanged. `SessionRecoveryRegistry` keeps bounded worker-local cache history, separately from aggregate cache fractions and official status feeds. Return decisions require matching failure recovery and this caller's own prefix/account cache evidence. Missing or newer negative evidence blocks an optional return. A sticky child start requires `AuthorizationSnapshot.descendant_start_authorized`; its default is false, so hosted root-funding checks must explicitly authorize that case.

Pool and deployment budgets may target reachable children of the active direct alias's pinned graph. Authoring validates the snapshot outside the database write lock, then rechecks the exact alias revision inside the write transaction. Snapshot files must be regular, non-symlinked, digest-valid local files. Root pool controls keep the existing no-file path. POSIX reads use directory-relative no-follow handles; Windows reads reject reparse points and hold checked directories against replacement until the file closes. Snapshot parsing has an adjustable authoring-only resource budget, defaulting to 64 MiB. This is not a catalog validity limit. Larger reviewed files can be admitted by setting `[gateway].budget_snapshot_max_bytes` in the project's existing `settings.toml`, or by passing `snapshot_max_bytes` to `SQLiteBudgetStore`. Values must be positive integers no greater than 2^63-1; the error states the required bytes and configured limit. No file I/O runs under the budget write lock. A refused child pool can be skipped only when the atomic ledger returns a `BudgetRefusalBinding` proving it is destination-only for this exact request after every applicable request-wide budget check passed; root, shared, unknown, and mismatched refusals stop the request. A hosted store with later request-wide checks must not issue that binding before those checks pass. Rejected pools are remembered only within that request, never as provider health.

## Snapshot authority and rollout

Budget authoring requires the current supported normalized snapshot schema. It rejects unknown fields at every validated level, then checks the published default-excluding catalog identity against the alias's pinned digest. It does not use the serving reader's tolerant cross-version path. A future schema, unknown policy, or digest mismatch requires rebuilding the snapshot with a supported engine and reactivating the alias before changing child budgets. Root pool controls still need no snapshot read.

An absent or empty `model_chains` field preserves the current pre-chain schema-5 identity. Pre-chain schema-5 readers refuse populated chains through their same-schema digest check. Older schema-4 readers treat schema 5 as foreign and can silently discard populated chain policy, including an explicitly unavailable model. The schema number therefore cannot make activation safe: those readers must be excluded by the host capability and rollback floor before any populated chain is published. Direct-only snapshots retain their existing cross-version serving compatibility.

Generic local SQLite serving refuses publication, registration, activation, and execution of populated chains. Draft `ModelCatalog` authoring and pure graph expansion remain supported, as do ordinary remote references and unchained serving. A preexisting local chain cannot fall back to a prior weaker alias revision. Local ownership locks and numeric schema versions are not fleet proof.

Local serving classification has its own per-file resource policy: `[gateway].serving_snapshot_max_bytes` in `<root>/settings.toml`, defaulting to 64 MiB (67,108,864 bytes). It applies independently to the normalized snapshot and its authored `.models.json` sidecar at registration, activation, startup, authorization, and reservation. This is a new serving resource bound, not a catalog validity limit, and changing the authoring-only `budget_snapshot_max_bytes` does not change it. To serve a reviewed larger direct-only catalog, explicitly raise the serving setting, for example:

```toml
[gateway]
serving_snapshot_max_bytes = 134217728 # 128 MiB per file
```

Values must be strict positive integers no greater than 2^63-1. Root-aware management loads this setting once when constructed; restart the gateway or reconstruct management after changing it. Database-only `SQLiteGatewayStore`, `SQLiteAttemptLedger`, and `SQLiteGatewayPlatform` constructors use the 64 MiB default unless passed `serving_snapshot_max_bytes` explicitly. They never guess a settings root from an arbitrary database path. Programmatic compositions must pass the same limit to their control and ledger components. Oversized files fail closed before serving work, with an error naming the required bytes, configured limit, and setting to adjust. They never become unchained or bypass the regular-file, no-symlink, mutation, shape, or populated-chain checks.

Local request authorization, acceptance, and reservation open fresh secure handles before acquiring the SQLite write lock. A composition-owned memo reuses only plain catalog classification for an unchanged normalized/authored pair. It retains no JSON, request permission, or host authority: at most eight pairs keep sixteen leaf identity anchors. Every operation independently checks the full path, both file generations, absence, and configured size bound. Leaf anchors prevent inode reuse between operations; the operation keeps its own handles through its write transaction, so eviction never closes live proof handles. Root-aware local components share one memo; standalone store and ledger constructors own one unless explicitly supplied a borrowed `classification_memo`. Call the owning component's `close()` when finished. Closing a borrower leaves its owner's memo alone. Closing the memo disables reuse, not any authority check.

A single process-wide permit bounds simultaneous cache-miss parsing using only the operation's remaining request deadline. The permit is released before any write transaction. Synchronous JSON parsing is not interruptible by that timer; expiration is checked before permission can be used and produces the ordinary pre-dispatch timeout without provider work. Each operation freshly fences the exact requested and active revision/digest/reference tuples plus no-follow path identities and file metadata under its write transaction. Missing files or sidecars must remain missing at the same path. A concurrent change fails closed for that operation; a new request can retry. Group-commit writers prepare on their existing connection before `BEGIN`, own proof handles even when a caller stops waiting, and clear memo anchors after draining. Direct internal `apply_*` calls require the matching live preflight rather than parsing under an already-open transaction.

On POSIX, classification reuse checks inode, path, size, modification time, and change time. It does not guarantee detection of raw filesystem mutation that preserves every observed identity and timestamp. Windows operation handles deny concurrent writes and replacement. Its optional memo anchors use metadata-only handles with read/write/delete sharing and check `FILE_BASIC_INFO.ChangeTime`, not Python's creation-time `st_ctime`. The canonical publisher uses same-directory atomic replacement. When ordinary Windows replacement returns access denied for an open destination, it uses `FileRenameInfoEx` with replace-existing and POSIX semantics; an unsupported kernel or filesystem refuses the write with the prior destination intact, never a copy/delete fallback. Read-only attributes and strict operation handles that deny delete sharing still block publication. Normal Windows delete-on-close semantics can delay final deletion until an anchor is evicted. If reliable optional anchor retention is unavailable, the operation classifies fresh secure bytes instead; failed secure reads, mutation checks, size checks, and authority checks still refuse. Large cold catalogs incur parsing cost, while unchanged warm generations avoid full reads and JSON parsing.

Publication classifies the whole document. Admission classifies the selected target's exact pool and model, so an unrelated chain in a shared hosted catalog does not block an independently plain alias. Unknown pool membership or a chain bound to another same-model pool is refused. The host still checks the stable alias's durable floor on every authorization; returning a protected alias to plain content does not remove that requirement.

Hosted serving requires the concrete `authorize_model_chain` authority operation, returning `AuthorizationSnapshot.model_chain_authority` bound to the organization, key, identity, request, stable alias, selected revision, catalog digest, process generation, expiry and monotonic feature epoch. The receipt records a host transaction; it is not a permission grant a caller can mint. The host revalidates durable issuance, key/grant authority, process eligibility and the alias floor in acceptance and every physical reservation, including retries. Expired receipts may be renewed only by that enforcing transaction. Settlement of already accepted work remains idempotent.

Hosts must reject unproved publication and activation under the same barrier used for registration and feature-floor transitions. A floor applies to all revisions of a protected alias, so empty republishing, last-good fallback and old writers cannot remove it. Old eligible processes and pending work must be drained before activation; supported deployment and rollback paths must prevent incompatible re-entry. A heartbeat, schema number, compiled marker, or version-tag ancestry alone is insufficient. The engine cannot enforce deployment admission for the host and makes no claim against an administrator bypassing database or filesystem authority.

Current-revision replay uses fresh caller and host authorization before looking up or joining the cached operation. Historical protected replay without verified exact completed-operation context is refused; the reserved `completed_replay` mode never authorizes dispatch or a new continuation. Full hosted enablement requires the actual Postgres, old-reader, process-drain, race and rollback tests, not only the controlled test-host fixture. Publishing the engine package alone does not satisfy this condition.

The compiled extension exposes `exp_gateway_native.MODEL_STAGE_CONTRACT_VERSION` as integer `1`. Contract 1 means the native data plane consumes each deployment's actual canonical model identity and stage-local throttle-redial schedule. It does not certify host authorization, funding, or recovery behavior. A host must also verify Python's model-chain contract. Missing, non-integer, or unknown native markers cannot be replaced with a package-version comparison: a higher-numbered build can still lack the required wire handling. Python refuses staged admission without this exact native marker; routes without model stages do not require it.

## Verification boundary

Pure tests cover graph expansion, immutable stage projections, policy budgets, expiry, and evidence scope. Native loopback tests exercise all three conversational APIs in streaming and non-streaming forms, checking requested alias, actual-model header, exact attempt order, and closed accounting. These controlled tests do not establish real-provider cache hits, billing invoices, or deployed platform compatibility. Those require tests of the actual released engine, platform, schema, and configuration together.
